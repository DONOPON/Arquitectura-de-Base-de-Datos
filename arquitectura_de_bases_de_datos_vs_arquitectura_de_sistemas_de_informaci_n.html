Propósito Pedagógico • Separación de Fronteras Arquitectónicas

¿Por qué confundimos el despliegue de software con el motor interno de datos?

En ingeniería de software y administración de datos, un error habitual es mezclar la Arquitectura del Sistema de Información (SI) —cómo se distribuyen interfaces, lógica de negocio y servicios— con la Arquitectura de la Base de Datos (BD) —cómo el SGBD organiza bloques en disco, buffers en RAM, paralelismo de CPU e infraestructura física/cloud.

Mapa de Fronteras en Nuestro Proyecto

Capa 1: Arquitectura del Sistema de Información (SI)

Dashboards en Streamlit / Power BI (Front-end) comunicándose vía protocolos TCP/IP con scripts Python ETL y agentes transaccionales (Middleware Cliente-Servidor).

Capa 2: Arquitectura Interna del DBMS (On-Premise)

Clústeres documentales en MongoDB Atlas alojando colecciones públicas masivas (INEVAL, INEC, INAMHI), delegando parches, hardware y elasticidad al proveedor.

Pregunta 2 • Guía de Estudio Ubicación Conceptual del Modelo Cliente-Servidor

¿Por qué es un error conceptual clasificar a Cliente-Servidor como una arquitectura interna de almacenamiento y procesamiento de BD?

El modelo Cliente-Servidor (en 2 o 3 capas) define la separación funcional y distribución lógica de procesos en un Sistema de Información (Front-end interactivo vs. servicios centrales). En contraste, la arquitectura interna de una Base de Datos Paralela/Distribuida describe cómo el motor SGBD acopla CPU, Memoria RAM y Discos físicos para ejecutar operadores relacionales.

Diagnóstico Conceptual: Haz clic en cada tarjeta para contrastar Mito vs. Realidad

MITO COMÚN #1 Clic para invertir

"Como mi app usa Cliente-Servidor en 3 capas, mi base de datos PostgreSQL ya tiene escalabilidad paralela interna."

Confunde el desacople de red entre interfaz y servidor con la capacidad física del motor de datos.

MITO COMÚN #2 Clic para invertir

"El protocolo TCP/IP entre Python y PostgreSQL define cómo se guardan los bloques en el disco duro."

Confunde el protocolo de comunicación de sesión con el gestor de almacenamiento (Storage Manager).

MITO COMÚN #3 Clic para invertir

"Cliente-Servidor es lo opuesto a Shared Nothing o Shared Memory en bases de datos paralelas."

Compara categorías ortogonales: una es topología de aplicación (SI) y la otra es topología de hardware DBMS.

Matriz Comparativa: Despliegue SI vs. Arquitectura Física DBMS

Síntesis técnica para sustentar la Pregunta 2 en examen o defensa oral.

Ortogonalidad Arquitectónica
Dimensión de Análisis Cliente-Servidor (2 / 3 Capas) Shared Memory (SMP) Shared Disk Shared Nothing (MPP)
Dominio Arquitectónico Sistema de Información (Software/Red) Interna del Motor DBMS (Hardware) Interna del Motor DBMS (Hardware) Interna del Motor DBMS (Hardware)
Acoplamiento de Recursos Separa UI, Lógica de Negocio y SGBD vía protocolos (TCP/IP, HTTP). Múltiples CPUs comparten 1 RAM global y 1 arreglo de discos. Cada nodo tiene CPU+RAM privada; todos comparten SAN/NAS. Cada nodo tiene CPU, RAM y Disco exclusivos; unidos por red de alta velocidad.
Cuello de Botella Principal Latencia de red entre cliente-servidor o saturación de conexiones. Contención en el bus de memoria RAM al superar ~16-32 cores. Contención en red SAN y sobrecarga del Distributed Lock Manager. Rebalanceo de datos (data skew) y transacciones distribuidas (2PC).

Pregunta 7 • Guía de Estudio Paradigmas Cloud: DBaaS vs. IaaS / PaaS / SaaS

Frontera Técnica de DBaaS (Database as a Service) y Balance entre Elasticidad y Vendor Lock-in

Un entorno DBaaS entrega motores de bases de datos listos para operar con elasticidad bajo demanda, respaldos automatizados y alta disponibilidad, abstrayendo el hardware y el sistema operativo, pero manteniendo expuesto el control lógico del modelo de datos, índices y consultas.
